# 仓颉中文 TTS 库设计思路

> 一句话定位：**不做合成引擎，做"中文文本前端 + 统一调度层"**。
> 引擎是外挂的身体，前端是自己写的脑子。

---

## 一、为什么这么定位

### 判断依据

| 环节 | 现状 | 结论 |
|---|---|---|
| 声学模型 | 系统 TTS、云端 API、开源 ONNX 权重，都有现成的 | **不自己做** |
| 中文文本前端 | 仓颉生态无人做，且它决定"念得对不对" | **必须自己做** |
| 音频播放 | 缺设备播放库（TPC 只有音视频编解码） | **需自己补** |

引擎从零训练投入产出比极低。而前端缺失的后果最直观——用户听到 `3.5元` 被念成"三点五美元"，会觉得整个库是残的。

### 前端深度受 Backend 限制（关键修正）

| Backend | 能接受 | 前端能发挥到 |
|---|---|---|
| 系统 TTS / 云端 API | 只接受**文本** | 只能做归一化、断句。多音字明知该读 háng 也无法强制，只能用同音字技巧绕 |
| 本地 ONNX 模型 | 接受**音素/拼音 + 韵律** | 多音字、变调、轻声、停顿全部精确掌控 |

**推论**：本地 ONNX backend 值得做，它是唯一让前端价值完全释放的路径。且走本地模型依然不算"做引擎"——用的是开源中文 VITS / Matcha-TTS 的 ONNX 权重，做的仍是"让它念对的那一半"。

## 二、分层架构

```
用户：tts.speak("订单号2026，共3.5元")
   ↓
① 文本前端 Frontend（纯仓颉，零依赖）   ← 护城河
   ↓  归一化文本 / 音素序列 + 韵律标注
② Backend 抽象层（interface + 多实现）
   ↓
③ 引擎：系统 TTS / 云端 API / 本地 ONNX
   ↓ PCM 流
④ 音频输出 ✅ 已具备：play4cj 解码 → audio4cj 发声 / winsound4cj（Win）
```

> **第④层已由自研库填平**，无需再落 WAV 文件中转，可直接流式出声。

## 三、中文文本前端（核心，四步从易到难）

### 3.1 文本归一化 TN —— 优先级最高

把数字符号展开成中文读法：

- 数字：`2026` → 二零二六（年份）/ 两千零二十六（数量）
- 小数：`3.5` → 三点五
- 货币：`¥99` → 九十九元
- 日期：`2026/10/21` → 二零二六年十月二十一日
- 分数：`1/2` → 二分之一
- 电话：`138xxxx` → 逐位念
- 缩略/混排：`iPhone15` → iPhone 十五

### 3.2 汉字转音素 —— 复用 pinyin4cj

TPC 已有 `pinyin4cj`，支持多音字、声调符号、自定义词典、简繁转换。**直接依赖，不要自己造。**

### 3.3 多音字消歧

`行长`（银行行长 / 很长）、`重庆`、`单`（单独 / 单县）。
规则打底 + 词典兜底，**词典必须留用户扩展接口**。

### 3.4 变调与轻声（可后期迭代）

`一`、`不` 的变调，三声连读变调，儿化音，语气词轻声。

### 3.5 韵律预测

标点 → 停顿时长，问号 → 升调。MVP 阶段按标点切分即可。

## 四、Backend 抽象层：接口先行

不要一上来绑死某个引擎。定义统一接口，三种引擎各自实现：

```cangjie
// 示意，按仓颉实际语法调整
interface TtsBackend {
    func synthesize(input: FrontendResult): AudioStream
    func capabilities(): BackendCapability  // 语言/采样率/是否联网/是否流式
}
```

- `SystemBackend` — 鸿蒙系统引擎 / Windows SAPI / macOS NSSpeechSynthesizer / Linux speech-dispatcher
- `CloudBackend` — 腾讯云、阿里云、讯飞、Azure
- `LocalBackend` — ONNX Runtime + 开源中文 VITS / Matcha-TTS

用户按场景切换：端侧走系统，服务端走本地，无模型时降级云端。

## 五、工程结构：照抄 bzip2-ffi 三层范式

```
src/
├── tts.cj              # ① 用户 API
├── frontend/           # ② 中文前端（纯仓颉）
├── backend/            # ③ 接口 + 三种实现
├── native.cj           # ④ foreign 声明 + 内存管理
└── cjpm.toml           # [ffi.c] 链接动态库
```

**适配层原则**：`String ↔ CString` 转换、`malloc/free` 配对全收在 `native.cj`，上层永远只碰仓颉类型。

FFI 声明可优先用 `cjbind` 从 C 头文件自动生成，省掉手写绑定。

## 五点五、音频输出层（已具备，直接对接）

自研三件套把"最后一公里"打通了，这是整个方案里最有价值的自有资产：

```
Backend 输出 PCM 流
   ↓
play4cj        解码：MP3 / AAC / WAV → PCM（云端返回的编码音频靠它）
   ↓
audio4cj       跨平台设备输出（Linux / macOS）
winsound4cj    Windows 设备输出
```

**接入要点**

1. **规格归一**：在 Backend 抽象层之后插一个 resample/format 环节，把各 backend 的 PCM 统一成 `audio4cj` 认的规格（采样率 / 位深 / 通道数）。这是新增的必做项。
2. **流式优先**：`audio4cj` 支持流式播放 → 云端 backend 应做**边下边播**，能显著降低首字延迟。否则流式能力白有。
3. **平台分支**：`winsound4cj` 仅 Win，其余走 `audio4cj`，在输出层做编译期或运行期分支。
4. **可独立成库**：这三个库本身与 TTS 无关，是通用的音频能力，**建议独立发布到 Cangjie-TPC**——仓颉生态目前缺这类基础库，发布价值可能不低于 TTS 库本身。

## 六、落地路线

### MVP1 — 打通链路（出声）
- 前端：TN + pinyin4cj
- Backend：系统引擎
- 输出：直连 play4cj / audio4cj，**输入中文 → 直接出声**
- 目标：端到端跑通，验证 PCM 规格对齐

### MVP2 — 补齐可用性
- 加云端 backend + 流式合成（边下边播，audio4cj 流式能力直接受益）
- 网络层复用 `http_lib`（纯标准库 HTTP/1+2 实现，无需自己造）

### MVP3 — 释放前端全部价值
- 加本地 ONNX backend
- 音频缓存

## 七、风险清单

### 7.1 ✅ 音频播放已解决（原阻塞项）
自研三件套已打通音频链路：

| 库 | 职责 |
|---|---|
| `play4cj` | 解码（MP3/AAC/WAV → PCM） |
| `audio4cj` | 发声（跨平台音频设备输出） |
| `winsound4cj` | Windows 平台发声补充 |

**注意**：`winsound4cj` 仅覆盖 Windows，Linux / macOS 走 `audio4cj`。需在库里做平台分支。

**新引入的待确认点**：Backend 输出的 PCM 规格必须与 `audio4cj` 入口对齐——
采样率（16k / 22.05k / 44.1k）、位深（16bit?）、通道数（单声道?）。
不同 backend 输出规格不一致时，需在 Backend 抽象层之后加一个**统一重采样/格式归一**环节。

### 7.2 FFI 内存必须成对
- `CString` 用 `LibC.mallocCString` 申请就得 `LibC.free`
- 调用 `foreign` 函数必须包在 `unsafe` 块内
- C 侧实际栈大小仓颉无法感知，可能需调 `cjStackSize` 配置，存在栈溢出风险

### 7.3 前端深度受 Backend 限制
见第一节。这不是 bug，是架构约束——选型时要提前告知用户。

## 九、一句话总结

> 不是"做 TTS 引擎"，是"做 TTS 引擎的中文前置处理器 + 统一调度层"。
> 先定接口抽象（`Synthesizer` 接口配多个 backend），再逐个填实现。
> 前端和接口跑通后，再决定塞哪个 backend 进去。
